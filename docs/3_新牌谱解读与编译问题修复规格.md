# 新牌谱解读与桌面版编译问题修复规格

## 1. 目标和结论

目标是让用户粘贴新的雀魂牌谱链接后，应用完成以下闭环：

```text
雀魂链接
  -> Chrome/CDP 提交 Mortal
  -> 找到真正的报告页
  -> 下载并校验 report.json
  -> 提取 Mortal 恶手
  -> 生成中文解读和坐标
  -> 更新 bad_moves.json、coach/<tag>.json、coach/index.json
  -> 前端加载新局并定位到第一处恶手
```

现有代码在旧报告上可以正常工作。用现有 `261118.json` 在临时副本运行
`pipeline_one.py --no-img` 的结果是：1016 个牌谱事件、167 个评测局面、24 手恶手、24/24 个坐标定位成功，`mk_coach.py` 成功更新。因此本次优先修复入口和错误可见性，不要先重写 `explain.py` 或重新训练 Mortal。

当前实际复现的根因是 `tools/submit_auto.mjs` 使用 `btn.click()` 触发表单。Chrome CDP 的 `Runtime.evaluate` 场景下，按钮 click 可能只执行页面事件而没有真正 POST 到 `/review`，页面一直停在首页，后续自然拿不到 Mortal 报告。改用 `form.requestSubmit()` 后，同一牌谱、同一表单字段和同一 Turnstile token 可以在约 12 秒内跳转到 `/killerducky/?data=/report/<id>.json`。此前的首页误判和相对 `data` URL 仍是需要保留的防御性修复。

## 1.1 `mjai-reviewer` 是怎样得到牌谱内容的

需要区分官方网页服务和 GitHub 仓库里的本地 CLI：

### 官方网页服务

官网首页的 `reviewForm` 是普通 HTML 表单，核心字段是：

```text
POST https://mjai.ekyu.moe/review
  input-method=log-url
  log-url=<雀魂/天凤牌谱 URL>
  player-id=<0..3 或空>
  engine=mortal
  mortal-model-tag=4.1b/4.0/...
  ui=killerducky
  lang=zh-CN
```

服务器端收到表单后负责下载牌谱源数据、按来源格式转换成 Tenhou/MJAI 事件、运行 Mortal、生成报告 JSON，然后重定向到 `killerducky/?data=/report/<report-id>.json`。本地应用不应该直接请求雀魂 `paipu` 页面来获得 Mortal 结果；雀魂链接只是官网表单的输入参数。

### GitHub 仓库里的本地 CLI

当前 `src/main.rs` 的本地链路是：

```text
Tenhou URL / Tenhou log ID / 本地 tenhou.net/6 JSON
  -> download::tenhou_log()
     GET https://tenhou.net/5/mjlog2json.cgi?<log-id>
  -> 解析 RawLog
  -> convlog::tenhou::Log
  -> tenhou_to_mjai(&log)
  -> Mortal Reviewer
  -> HTML 或 JSON 报告
```

`src/download.rs` 只下载天凤日志；`mjsoul.adoc` 说明雀魂日志需要额外的登录、下载和格式转换步骤，历史上曾通过 `tensoul` 服务完成。当前本地 CLI 的普通 `--url` 分支并不等于浏览器官网对雀魂链接的服务端适配。

### 对本项目的直接要求

```text
Chrome + Turnstile
  -> 在官网 reviewForm 填字段
  -> form.requestSubmit(submitButton)
  -> 轮询 /progress 和 /killerducky/?data=...
  -> 下载 /report/<id>.json
  -> 本地 pipeline_one.py 生成中文解读
```

本次实测同一雀魂链接成功得到：

```text
SUBMIT requestSubmitted
https://mjai.ekyu.moe/progress?task=5d8c9d3e1cfa1502
REPORT https://mjai.ekyu.moe/killerducky/?data=/report/5d8c9d3e1cfa1502.json
```

如果日志只出现 `SUBMIT clicked` 后停留在首页，说明表单没有真正 POST；如果进入 `/progress` 但没有 `REPORT`，才是官网排队、牌谱来源、座次或服务端转换失败。

## 2. 优先级和修改范围

### P0：必须先修

#### P0-1 使用 `requestSubmit()` 发起真实 POST

文件：`tools/submit_auto.mjs`，提交表单的 CDP 代码。

修改要求：

1. 填完字段后调用 `f.requestSubmit(submitButton)`。
2. 不要把 `btn.click()` 作为现代 Chrome 的主路径；只能作为极旧浏览器兼容回退。
3. 日志必须出现 `SUBMIT requestSubmitted`，随后 URL 应从首页变成 `/progress` 或直接进入报告页。
4. 仍保留页面原生校验和 `reviewFormSubmit()`，不要改成绕过校验的 `f.submit()` 主路径。

#### P0-2 报告页识别过宽

文件：`tools/submit_auto.mjs`，报告轮询代码。

现状：

```js
if (!o.u.includes('zh-cn.html') && !o.u.includes('/progress')) {
  out = o.u;
  console.log('REPORT', out);
  break;
}
```

问题：主页、错误页、尚未提交成功的页面都可能通过条件。后续 `main.py` 报“报告地址里没有数据参数”，但用户看不到提交到底失败在哪一步。

修改要求：

1. 使用 `new URL(o.u)` 解析 URL。
2. 只有满足明确条件才打印 `REPORT`：pathname 是 `/report` 或 `/report/...`，或者 pathname 含 `killerducky` 且存在非空 `data` 查询参数。
3. 明确排除首页、`/progress`、语言首页、错误页。
4. 在报告页确认 `data` 参数存在，再等待页面渲染；超时输出最后 URL 和页面标题。
5. 输出机器可解析的错误标记，例如 `NO_REPORT_URL`、`REPORT_TIMEOUT`、`REPORT_URL <url>`。保留 `NO_PAGE`、`NO_TOKEN`。
6. 提交前后记录 URL，避免调试时无法区分“没有拿到 token”“表单未提交”“Mortal 排队中”。

#### P0-3 `data` URL 必须统一解析

文件：`app/main.py`，约 184-201 行。

修改要求：

1. 不要手写正则拼接主机；使用 `urllib.parse.urlparse`、`parse_qs` 和 `urljoin`。
2. 允许以下形式：绝对 HTTPS URL、`/xxx/report.json`、`report/xxx.json`。
3. 只允许 HTTPS 且主机为 `mjai.ekyu.moe`（必要时用配置允许其他服务），防止报告参数被利用下载任意本地/远端地址。
4. URL 解码后先 `urljoin(report_url, data_value)`，再下载。
5. 检查 HTTP 状态、`Content-Type`（允许 JSON）、JSON 顶层结构，并确认包含 `mjai_log` 或 `review`；只解析成功不代表是 Mortal 报告。
6. 下载到临时文件，校验通过后使用原子替换写入 `assets/kd/report/<tag>.json`，避免半个 JSON 被前端读到。

#### P0-4 流水线必须返回真实状态

文件：`scripts/pipeline_one.py`、`scripts/mk_coach.py`、`app/main.py`。

现状：`pipeline_one.py` 会打印成功信息，但 `mk_coach.py` 失败时只打印日志；`app/main.py` 只截取最后 120 个字符。没有恶手时也是 return code 0，前端无法区分“没有超过阈值”和“解读根本没生成”。

修改要求：

1. 为每局写 `assets/kd/coach/<tag>.status.json`，至少包含：
   - `tag`、`report_path`、`pipeline_version`、开始/结束时间；
   - `report_valid`、`events`、`reviewed`、`entries`；
   - `matched`、`threshold_filtered`、`explain_ok`、`explain_failed`；
   - `position_ok`、`position_missing`、`coach_moves`；
   - `stage`、`ok`、`error_code`、`error_message`。
2. 每条 `X.gen(rec)` 单独捕获异常，记录事件号并继续处理其他恶手；如果有失败，最终状态为 `partial`，不能伪装成完全成功。
3. `mk_coach.py` 非零退出必须让 `pipeline_one.py` 非零退出，并写入失败状态。
4. `recs == []` 是合法结果，状态应为 `ok`，并明确 `no_bad_moves: true`；界面显示“本局没有超过 10pt 阈值的恶手”，不能显示“解读生成失败”。
5. `app/main.py` 根据状态文件返回 `ok`、`partial` 或 `failed`，返回对象包含 `tag`、`stage`、`bad_moves`、`msg`。前端据此显示准确状态。
6. 保留完整日志到 `data/logs/<tag>.log` 或 `data/work/<tag>.log`，不要只把最后 120 个字符返回给用户。

## 3. 新牌谱状态机

`Api.submit_link()` 应按下列状态推进，任何失败都落状态文件并可重试：

```text
IDLE
  -> VALIDATING_INPUT
  -> CHROME_READY
  -> TOKEN_READY
  -> SUBMITTED
  -> REPORT_URL_READY
  -> REPORT_DOWNLOADED
  -> REPORT_VALIDATED
  -> EXTRACTING
  -> EXPLAINING
  -> POSITIONING
  -> COACH_EXPORTING
  -> READY
```

失败状态至少包括 `INPUT_INVALID`、`CHROME_UNAVAILABLE`、`NO_TOKEN`、
`SUBMIT_TIMEOUT`、`NO_REPORT_URL`、`REPORT_DOWNLOAD_FAILED`、`REPORT_SCHEMA_INVALID`、
`EXTRACT_FAILED`、`COACH_EXPORT_FAILED`、`PARTIAL`。

标签生成仍可以使用 `YYMMDD`、同日 `B/C/...`，但应在写入前再次检查文件是否已存在，避免两个提交并发时覆盖同一标签。建议增加进程级锁，提交按钮在请求期间禁用。

## 4. 前端刷新问题

文件：`assets/kd/index.js`，约 2430-2492 行。

现状：`submitLink()` 收到成功后调用 `initLibrary()`，随后立即跳转到新 report。`loadCoach()` 捕获所有异常并设置 `COACH = null`，没有告诉用户 coach 文件缺失。

修改要求：

1. Python 返回 `ready` 前必须保证 report、`coach/<tag>.json` 和 `coach/index.json` 已写完。
2. `initLibrary()` 后验证 `coach/index.json` 包含返回的 tag，并 `fetch(coach/<tag>.json, {cache: 'no-store'})` 验证 HTTP 200 和 JSON 结构。
3. 若状态是 `partial` 或 coach 尚未可读，轮询 1 秒、最多 10 次；期间显示“报告已下载，解读仍在生成”。
4. `loadCoach()` 不要吞掉异常，至少把 URL、HTTP 状态和 JSON 错误写入状态栏/调试日志。
5. 新局准备完成后再跳转，并带上第一处有效坐标；若 `moves` 为空，跳到新局但显示“本局没有超过阈值的恶手”。
6. 检查中文翻译是否覆盖原始 HTML 的 `Prev Round`、`Next Round`、`Prev Error`、`Next Error`、`Prev Choice`、`Next Choice`、`Options`、`About` 等文本。中文适配应是默认语言，而不是只依赖浏览器 localStorage。

## 5. 解读算法回归点

文件：`scripts/extract_core.py`、`scripts/explain.py`、`scripts/mjcalc.py`、`scripts/mjeval.py`。

现有算法在当前 12 份报告上应先保持结果不变，修改时增加 fixture 和计数，不要凭直觉改判定口径。

### 必须加的输入校验

- `mjai_log` 存在且为数组。
- `review.kyokus[*].entries` 存在且为数组；每条 entry 有 `state.tehai`、`tile`、`actual`、`expected`、`details`。
- `action` 的 `type/pai` 组合可被 `akey()` 处理，`q_value` 是数字。
- `seat` 在 0-3；缺失时只能使用明确的推断规则，并在状态文件记录 `seat_source`。
- `kyoku`、`bakaze`、`honba`、`scores` 缺失时使用可见的默认值并记录 warning。

### 必须统计的对齐指标

`extract()` 现在找不到指纹时直接 `continue`。应返回或记录：entries 总数、self/call 分类数、指纹匹配数、重复去重数、缺失坐标数、缺少候选 Q 值数、阈值筛掉数。这样新 Mortal 格式变化时能明确判断是“无恶手”还是“全部无法对齐”。

### 需要 fixture 回归的牌型

1. 自摸后打牌、摸切和立直动作。
2. chi、pon、daiminkan、ankan、kakan 后的状态。
3. 同一手牌指纹重复出现时的 `last_used` 行为。
4. 红宝牌与普通牌的 action key 是否被错误合并。
5. `visible_counter()` 对河牌、鸣牌、宝牌指示牌的重复计数。
6. E1/S4 等局数下自风、场风、亲家和点棒顺位文本。
7. `gap >= 0.30` 的边界值，以及 Mortal 原始概率字段存在时是否应优先使用原概率。

算法说明必须继续强调：Mortal 的 Q 值和 softmax 概率是策略选择倾向，不是点数损失、和了率或放铳率。自然语言只能使用本地计算出的向听、受入、可见牌、安全度和点棒条件。

## 6. `rebuild_all.py` 的补齐逻辑

文件：`scripts/rebuild_all.py`，约 32-44 行。

现状只判断 coach 文件不存在或 `moves` 为空。以下坏状态会被误认为已完成：旧版本字段不完整、坐标全部为 `None`、report 的 entries 数量已变化、解读文本为空、状态文件显示失败。

修改要求：

1. 读取 report、`data/work/<tag>.json`、coach 和 status 文件做一致性检查。
2. 至少比较 report 的 `total_reviewed`/entries 数、bad move 数、coach moves 数和 `pipeline_version`。
3. `moves == 0` 只有在 status 明确 `ok + no_bad_moves` 时才视为完成。
4. 发现 `partial`、`failed`、坐标缺失比例异常、字段缺失或版本过期时自动加入待处理列表。
5. 每局失败继续处理下一局，最后以非零退出码报告失败局列表，方便 bat/CI 发现问题。

## 7. 独立 EXE 和编译逻辑

文件：`app/main.py`、`docs/1_编译思路.md`、根目录两个 `.bat`。

### 当前不一致

README 把应用描述为“自包含”，但实际 EXE 仍依赖：

- `C:\Users\<用户名>\.workbuddy\binaries\python\envs\default\...` 中的 Python 和 Pillow；
- 外部 Node.js（`find_node()` 只硬编码 Workbuddy 路径和 `C:\Program Files\nodejs\node.exe`，当前机器实际 Node 还可能在其他目录）；
- Chrome、Chrome 的 CDP 9222、Cloudflare Turnstile；
- WebView2 Runtime；
- EXE 旁边的 `assets/`、`scripts/`、`tools/`、`data/`。

冻结后 `sys.executable` 是 `mortal-coach.exe`，不是 Python 解释器。若目标机器没有 Workbuddy Python，`pipeline_one.py` 会被错误地交给 EXE 执行。Node 也没有随 EXE 打包。因此“只拷贝一个 exe 即可运行”不成立。

### 推荐方案

短期：明确发布包为目录包，并在启动时做依赖自检：

```text
mortal-coach.exe
assets/
scripts/
tools/
data/
runtime/python/   # 随包提供 python.exe + Pillow 等依赖
runtime/node/     # 随包提供 node.exe
profile_mj/
```

`find_py()`、`find_node()` 优先查 `ROOT/runtime/...`，再查环境变量，最后才查系统 PATH。启动失败要弹出可读的缺依赖提示，不要把 EXE 当 Python 解释器。

中期：如果必须单文件，再把 Node 和 Python 作为 sidecar 解压到临时目录，并明确处理杀毒软件、首次启动和版本升级；这不应由当前 agent 顺手完成。

编译验收不能只在当前开发机运行，必须在没有 `.workbuddy` Python、没有系统 Node 的干净 Windows 虚拟机验证“启动已有报告”和“提交新牌谱”两条路径。`docs/1_编译思路.md` 和 README 应改成真实的发布前置条件。

## 9. 测试和验收标准

### 自动化测试

- `python -m compileall app scripts` 通过。
- URL 解析测试覆盖绝对、根相对、路径相对、缺失 data、非允许主机。
- 报告 schema 测试覆盖合法报告、空 review、缺 mjai_log、损坏 JSON。
- 用现有报告 fixture 运行 extract：每局输出 entries、匹配数、恶手数；结果与当前基线一致。
- `X.gen()` 逐条运行，任何单条异常都不会中断整局，并在 status 中可见。
- `rebuild_all.py --no-img` 能识别正常、无恶手、partial、过期四种状态。

### 手工验收

1. 首次启动已有报告，侧栏能打开最近一局；没有外部 Python/Node 时提示缺依赖而不是静默失败。
2. 粘贴一条新雀魂链接：Chrome 可拿 token，提交成功后能看到真实报告 URL，下载 JSON，生成 coach 文件，并自动跳到新局。
3. 新局有恶手时，界面直接停在第一处恶手；新局无恶手时显示“本局没有超过阈值的恶手”。
4. 模拟 Mortal 首页、progress 超时、报告 404、JSON 损坏、pipeline 失败，界面分别显示可操作的错误原因。
5. 连续提交同日两局不会覆盖，生成 `YYMMDD`、`YYMMDDB` 两个标签。
6. 重启应用后新局仍在 `coach/index.json`，解读和坐标可正常加载。

### 完成定义

只有同时满足以下条件才算完成：

- P0 三项均有自动化测试和手工验证；
- 正常新牌谱从链接到解读在一次点击内完成，或明确显示当前阶段；
- 任意失败不会生成“完成”假象，且可从 status/log 定位；
- 干净机器能按发布说明运行已有报告；
- 当前旧报告的恶手数量、坐标和中文解读没有无证据变化。

## 10. 暂不建议直接改动

- 不要为了修复新牌谱入口重写 Mortal 评分或 `explain.py` 的全部文案。
- 不要把 Q 值直接解释成点棒损失、胜率或放铳率。
- 不要把 Mortal 权重、Chrome 用户凭证或 API key 打进 EXE。
- 不要只通过增加等待时间掩盖报告 URL 判断错误。
- 不要在没有 fixture 的情况下调整提取门槛（`extract_core.THRESH`，当前 10pt）、softmax 温度或鸣牌可见牌口径。

## 11. 本轮桌面版使用问题修复

本轮实现补齐了三个影响日常使用的入口问题：

1. **后台进程生命周期**：Chrome、Node 和 Python 子进程使用 Windows 隐藏窗口参数，分析结束只关闭本次应用启动的 Chrome；如果 9222 已经由用户浏览器占用，应用不会接管或关闭它。Chrome 增加启动参数，避免出现黑色控制台和“Chrome 未正常关闭”的恢复提示。
2. **粘贴行为与 Mortal 一致**：输入内容会从第一个 http(s) 开始截取，并清理复制文本末尾标点。粘贴 killerducky/?data=/report/...json 或 /report/...json 时直接下载并校验 Mortal 报告，进入本地解读流水线，不会把结果页误提交为雀魂源牌谱。普通雀魂/天凤链接仍通过官网表单和 Chrome 提交。
3. **空白首页与历史记录**：应用启动到 ?view=home，不再自动打开最近一局，也不会因缺少 data 参数弹窗。首页保留牌谱输入、模型和座次选择，并提供按年/月/日筛选的历史列表；“查看”打开对应牌桌，“删除”会确认后清理报告、解读、日志、图片和恶手记录并重建 coach/index.json。

    runtime\node\node.exe tools\test_rules.mjs
    runtime\python\python.exe tests\test_urls.py
