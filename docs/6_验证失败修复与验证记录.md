# 验证失败修复与验证记录（2026-11-21，提交脚本 build 5）

> 本文是历史实现与修复记录；当前安装和验证流程请以 [使用说明](../使用说明.md) 与 [后台分析／首次验证](8_后台分析与新机器首次验证.md) 为准。
## 现象与判断

用户反馈：日常浏览器可以通过 Mortal 的真人验证，应用启动的独立浏览器显示红色「验证失败」。两者使用不同的浏览器资料目录，日常浏览器成功不代表应用窗口已经获得验证。

已确认应用存在三个独立缺陷：

1. 应用启动浏览器时已打开首页，提交脚本再次导航首页，可能重置刚在设置窗口完成的验证。
2. 隐藏窗口模式会自动派发验证点击，等待后自动刷新，可能打断人工处理。
3. 只有“没有 token”的超时分支，无法区分已失败与仍在等待，且缺少恢复和普通浏览器入口。

隔离资料目录对照中，现有参数与精简参数都能打开首页，均未获得验证响应，未观察到具体 Cloudflare 错误码。测试没有自动点击或完成验证码。因此尚不能认定某一启动参数、IP 或代理就是远端拒绝的原因，也不能宣称所有机器已可自动通过验证。

## 已实施的修改

- 首次提交复用已打开的 Mortal 首页，保留设置中刚完成的验证；继续等待不导航。
- 移除程序对验证码的自动鼠标点击、定时重载。需要人工操作时显示窗口。
- 被动观察来自 Cloudflare 的控件失败消息，只匹配 reviewForm 的响应 ID，不把另一套 botForm 控件错误当作复盘失败。只记录六位错误码或 unknown，不输出验证令牌。
- 增加 verification_failed 状态，保留原任务参数和浏览器；未完成的等待仍归类为 verification_pending。
- 增加「重新加载验证」。等待中的请求通过子进程标准输入传递；脚本只在提交之前、确认仍是官网首页表单时执行。已进入提交或评分阶段时拒绝重载。
- 增加「使用普通浏览器生成报告」。先取消正在运行的任务；入口打开系统默认浏览器的官网，链接通过官网支持的 url 参数预填。模型和座次由用户在官网核对。生成报告后将最终报告地址贴回应用，直接下载并生成中文解读。
- Python 与外置提交脚本协议号同步为 5，并重新编译 EXE。既有系统浏览器优先策略和独立持久资料目录保留。

## 用户操作

直接启动本地更新后的 mortal-coach.exe，粘贴牌谱并分析。需要验证时在浏览器内操作，完成后自动继续。不要在评分期间重载网页。

若仍显示红色失败，点应用中的「重新加载验证」。普通浏览器可以通过时，取消本次任务，点「使用普通浏览器生成报告」，在官网生成最终报告；复制报告页完整地址回应用点「分析」。不要复制排队页 /progress。
